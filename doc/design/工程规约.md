# 工程规约

> 版本：v1.0
> 日期：2026-10-26
> 适用范围：JAVA-LEARN 全部代码、脚本、Compose、面板、测试与文档
> 关联：`doc/design/Stage1/2026-10-26-ha-concurrency-lab-design.md`

## 1. 配置外置（强制）

所有可运行的路径和参数必须可从配置覆盖，不得在 Java 代码、配置模板或脚本中写死：

- **路径**：文件、目录、URL、URI 前缀、挂载点、日志、快照、构建产物、数据目录。
- **时间/数量参数**：超时、重试次数与退避、TTL、缓存容量、连接池/线程池大小、端口、并发度、批量大小、保留期。
- **敏感值**：token、密码、证书只放环境变量或 `.env`，不提交仓库。

落地方式：

- Spring 侧使用 `application.yml` + `@ConfigurationProperties`；提供安全默认值，但必须能被环境变量覆盖。
- Compose 使用 `${VAR:-default}`；脚本把可调参数集中到变量或 `.env.example`；场景参数放 JSON。
- Dockerfile 中会影响运行的路径/版本尽量用 `ARG`；构建期固定路径如确无运行期变化，需在文档说明。
- 禁止新增魔法值（如 `10_000`、`60s`、`300s`、`10 × 50ms`、端口、`/app/app.jar`）直接散落在业务代码里。
- 测试中的固定断言值不属于运行配置；但测试 fixture 的路径/超时也应优先可配置。

评审要求：

- 每个任务的评审必须检查“是否有新的硬编码路径/超时/容量”；发现后在**同一任务内**修复并补测试。
- 触摸到旧硬编码时顺带外置，不要求一次性全量重构。
- 已有的硬编码清单见 `doc/process/STAGE-01阶段交接-2026-10-26.md` 的“存在缺陷项&TODO”。

## 2. 每步交接文档（强制）

每个任务或修复步骤结束后，在当前阶段的 `doc/process/Stage<N>/` 新增交接文档（`step-*.md`）并随代码提交；阶段收口文档放在 `doc/process/` 顶层，命名 `STAGE-<NN>阶段交接-<日期>.md`。固定章节：

1. `# 当前进展`
2. `# 完成功能项`
3. `# 设计逻辑`
4. `# 存在缺陷项&TODO`
5. `# 待定事项和注意事项`

允许增加附录（启动/验证命令、提交、关键文件、证据）。使用 `doc/process/交接模板.md`。没有新增也要写“本步无新增”。文档至少要包含：最新 commit、测试/verify 结果、已知缺陷、下一步。

## 3. 演示优先

项目目标始终是“制造缺陷/故障 → 观察症状 → 执行处理 → 对比效果”，不是生产级秒杀系统。不添加录屏、旁白、回放。

## 4. 评审执行

### 4.1 工具与隔离

任务代码审核在**独立 Qoder 会话**中执行，使用 **Qwen 3.8-代码审核修复子代理 + 隔离 git worktree**；主开发会话继续推进，审核会话不得修改主工作树或共享 Docker 栈。审核只跑单元/Testcontainers 测试，High/Medium 修复在 worktree 提交，主会话合并后统一 verify。Open Code Review（OCR）需要额外 LLM 配置，按用户决定**暂不启用**；`doc/design/OpenCodeReview-使用手册.md` 仅保留备查。

### 4.2 评审内容

评审同时检查：

- 规范符合性与代码质量；
- 配置外置（路径、超时、TTL、池大小、端口）；
- 测试是否验证真实行为；verify 是否被弱化；
- 是否引入未被要求的业务/生产加固；
- 敏感信息与宿主机暴露；
- 演示可用性与可暂停/可还原。

Critical/Important 必须修复或按流程裁决；Minor 记录在案，后续任务顺带处理。修复在隔离 worktree 内完成，主会话负责合并与全量 verify。

## 5. 生效与历史

- 本规约强制执行。
- 历史代码中的硬编码在交接文档中登记，作为后续评审/清理项，不在本规约生效时一次性重构。
