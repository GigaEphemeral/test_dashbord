# 数据库高可用方案对比

- 日期：2026-10-26
- 状态：随主设计评审
- 主文档：[本地高可用 / 高并发演示实验室 · 整体设计](2026-10-26-ha-concurrency-lab-design.md)

本项目采用 **方案 A：MySQL InnoDB Cluster（3 节点组复制）+ MySQL Router**。本文保留方案 B 的完整描述与优缺点，作为备选与回退路径。

---

## 1. 对比总览

| 维度 | 方案 A：InnoDB Cluster + Router（采用） | 方案 B：主从复制 + ProxySQL（备选） | 方案 C：单机（dev） |
|---|---|---|---|
| 拓扑 | 3 × MySQL（Group Replication，单主）+ 1 × Router | 1 主 + 2 从 + 1 × ProxySQL | 1 × MySQL |
| 自动选主 | 有，组复制选举，秒级 | 无，需脚本晋升从库并切换流量 | 无 |
| 读写分离 | Router 6446 读写 / 6447 只读 | ProxySQL 规则分流 | 无 |
| 客户端接入 | 连接 Router，应用无感切换 | 连接 ProxySQL | 直连 |
| 数据一致性 | 认证式复制，冲突事务回滚 | 异步复制，可能丢数据 | 单机 |
| 资源占用 | ≈ 1.8GB | ≈ 1.2GB | ≈ 512MB |
| 启动时间 | 1–2 分钟，初始化脚本较复杂 | 30–60 秒 | 数秒 |
| 演示透明度 | 切换过程偏黑盒，靠指标与日志观察 | 每一步命令可见，利于讲解失败与恢复 | 只能演示单点故障 |
| 运维复杂度 | 高 | 中 | 低 |
| 与项目目标匹配 | 自动故障转移真实、接近生产 | 切换逻辑可完全讲解 | 仅用于日常开发 |

## 2. 方案 A：InnoDB Cluster + Router（采用）

### 2.1 架构

```
app-1/2/3
   │  读写 6446 / 只读 6447
   ▼
mysql-router
   │
   ├── mysql-1（初始主）
   ├── mysql-2
   └── mysql-3
     Group Replication（单主模式）
```

### 2.2 工作方式

- 三节点组成 InnoDB Cluster，单主模式下只有一个可写节点
- 主节点故障时，组复制自动选出新主；Router 感知拓扑变化并把读写流量切到新主
- 应用连接 Router，不在配置中写死某个节点的地址
- 读写分离：应用中 `@Transactional(readOnly=true)` 的请求走 6447，其余走 6446
- 集群状态由 chaos-controller 定期通过 mysql-shell 查询，暴露成员状态与当前主节点

### 2.3 优点

- **真正的自动故障转移**，符合"高可用"演示主题，切换过程不需要人工介入
- 读写分离由 Router 完成，应用侧只需要处理数据源路由
- 接近生产实践的组复制模型，教学价值高
- 成员状态、主节点角色可观测，配合 Grafana 标注能清楚看到角色翻转

### 2.4 缺点与风险

- 初始化脚本复杂：组复制参数、cluster 引导、Router 引导都需要顺序正确
- Docker Desktop（WSL2）下镜像初始化偶发失败，需要重试与健康检查
- 资源占用较高（约 1.8GB），启动慢，影响日常开发时的启动体验
- 切换过程对外表现偏黑盒：只能通过指标、Router 日志和成员状态间接观察
- 组复制是认证式复制，冲突事务会回滚；网络分区时可能短暂不可写
- MySQL Router 本身是单点（本地实验接受，生产需多实例 + LB）

### 2.5 启用方式

- `compose.ha.yml` 启用 3 节点 + Router；`compose.dev.yml` 使用单机 MySQL
- 应用通过环境变量切换连接串，镜像不变
- 初始化脚本 `code/lab/docker/mysql-cluster/init.sh` 负责引导集群并等待 READY
- 初始化失败时脚本可重跑，且不破坏已有命名卷

## 3. 方案 B：主从复制 + ProxySQL（备选）

### 3.1 架构

```
app-1/2/3
   │
   ▼
proxysql（读写分离 + 健康检查）
   ├── mysql-master（可写）
   ├── mysql-replica-1（只读）
   └── mysql-replica-2（只读）
```

### 3.2 工作方式

- MySQL 原生异步（或半同步）主从复制，GTID 开启
- ProxySQL 按规则把写流量送主库、读流量分摊到从库，并做后端健康检查
- 主库故障时，由 chaos-controller（或独立切换脚本）执行：
  1. 检查从库复制位点与延迟
  2. 选择一个从库执行 `STOP REPLICA`、`RESET REPLICA ALL`
  3. 将其提升为新主（`SET GLOBAL read_only=OFF`）
  4. 其余从库指向新主
  5. 更新 ProxySQL 后端分组
  6. 记录切换耗时与错误窗口
- 整个过程每一步都有明确命令，页面可展示执行日志

### 3.3 优点

- 配置简单、资源占用低、启动快
- **切换过程完全透明**，适合逐步讲解"为什么要提从、怎么防脑裂、怎么接回旧主"
- ProxySQL 自带查询统计，便于展示读写分流效果
- 对 Windows + Docker 环境更友好，初始化失败概率低

### 3.4 缺点

- 不是自动选主：切换依赖外部脚本，脚本本身就是需要讲解与保护的部分
- 异步复制可能丢数据；半同步配置会增加复杂度
- 需要自行处理脑裂防护、旧主恢复、复制重建
- 与"自动故障转移"的真实生产形态有差距

### 3.5 何时切换到方案 B

- InnoDB Cluster 在当前 Docker Desktop 环境反复初始化失败，且短期内无法稳定
- 演示更强调"切换过程可讲解"而不是"自动选主"
- 机器内存紧张，需要压缩到 12GB 以下

切换到方案 B 的影响面：

| 影响点 | 变化 |
|---|---|
| compose | 替换 MySQL 集群与 Router 为主从 + ProxySQL |
| 应用数据源 | 连接串改为 ProxySQL 地址；读写路由仍可保留 |
| chaos-controller | 需要实现提从、ProxySQL 更新、旧主接回动作 |
| 面板 D11 | 指标改为 ProxySQL 后端状态与复制延迟 |
| 验收场景 | `db-failover` 的判定不变，但切换由脚本完成 |

## 4. 方案 C：单机 MySQL（dev）

- 仅用于日常开发与快速启动（`compose.dev.yml`）
- 保留完整业务与监控，但不具备高可用能力
- 不作为任何高可用场景的验收环境
- 用于本地快速改代码、跑单测与 smoke 压测

---

## 5. 读写分离的实现细节

两种方案都需要应用侧配合：

- `ReadWriteRoutingDataSource`：根据当前事务是否只读选择目标数据源
- **必须配合 `LazyConnectionDataSourceProxy`**：Spring 在事务开始前可能已获取连接，直接使用 `AbstractRoutingDataSource` 会读到错误的 `readOnly` 标记。这是本项目已知的坑，会记录进 `doc/避坑/`
- 只读事务只允许执行查询；写操作必须在读写事务中完成
- 读延迟敏感的业务（如下单后立即查订单）强制走主库，通过 `@Transactional(readOnly=false)` 或显式指定数据源

---

## 6. 决策

采用方案 A，理由：

1. 项目主题是高可用演示，"自动选主 + 自动切流"是最直观的高可用证据
2. InnoDB Cluster 的成员角色变化可以直接画到 Grafana，与现有观测体系契合
3. 方案 B 的对比与回退路径已完整记录，初始化风险有兜底，不会阻塞其他场景
4. 日常开发使用方案 C，避免集群启动成本影响迭代速度

验收要求：`db-failover` 场景中，杀主后错误窗口 < 15s、错误率 < 1%，且 D11 能看到主节点角色翻转。
