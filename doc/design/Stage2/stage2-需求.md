在 Stage1 已有的 Java 高并发与高可用实验室上，建设一套可由 UI 配置、启动、注入故障、压测、实时观测、对比和复盘的 Java 性能与高可用演练工作台。

这不是推倒重做。现有 Docker Compose、三实例负载均衡、故障编排、k6、Prometheus、Grafana、Tempo、Redis/MySQL 高可用拓扑都应尽量复用。Stage2 的核心工作是把现有能力整合成一套完整、可重复、结果可验证的实验流程。

“几个 Java 实例代码完全一致，但 JVM、缓存等配置不同”，完全可行，而且非常适合做性能对比实验。作为 Stage2 的正式需求

## 一、先明确整体架构

根据当前文档，Stage1 已经具备以下基础：

- 入口层：Nginx 负责业务请求转发、操作台静态页面和部分内部 API 代理。
- 应用层：`jl-app-1/2/3` 使用同一应用镜像，默认运行在 JDK 21 环境下。
- 数据层：MySQL、Redis、RabbitMQ，以及可选的 Redis Sentinel、MySQL InnoDB Cluster + Router。
- 实验控制层：`jl-chaos-controller` 负责容器操作、故障编排、日志和背景流量控制。
- 监控层：Prometheus、Grafana、Tempo、OTel Collector、cAdvisor 及各类 Exporter。
- 压测层：k6 场景和容器化 Runner 已存在，但当前多种正式压测仍需通过脚本启动。
- 操作台：Vue 3 页面已经存在，但部分功能仍分散在 Grafana、命令行和内部 API 中。

当前缺口不在于完全没有监控或实验能力，而在于缺少统一的配置入口、实验执行流程、指标归集、结果对比和业务正确性判定。

## 二、Stage2 完整需求描述（需求基线 v1）

以下先整理成一份可以继续评审、拆分开发任务和编写验收用例的需求基线。为避免把设计目标和现状混为一谈，我会标出：

- 现有基础：Stage1 文档确认已具备的能力。
- Stage2 目标：需要整合、补齐或新增的能力。
- 验收要求：最终必须能实际操作、看到指标并验证结果，而不只是 UI 上有按钮。

### 2.1 建设目标

系统应提供统一的 Java 性能与高可用演练控制台，使使用者能够：

1. 通过 UI 选择 Java 实例、JVM 版本、JVM 参数和应用运行配置。
2. 通过 UI 控制缓存策略、实验数据规模、Redis 与 Caffeine 的缓存条目数量。
3. 通过 UI 配置并启动 k6 benchmark，包括并发用户数、运行时长、流量场景和压测阈值。
4. 手动制造、暂停、恢复和撤销故障，包括线程、应用实例、Redis、MySQL、网络和缓存相关故障。
5. 在控制台中直接查看 Prometheus/Grafana 监控，并查看按实例、实验和时间窗口归集的关键指标。
6. 对比不同 JVM、缓存配置、实例配置及故障场景下的吞吐量、延迟、资源占用和业务正确性。
7. 保存实验配置、故障事件、指标结果和判定结论，以便重复实验和回看历史结果。

核心原则：相同业务代码，不同运行环境与配置，通过同一套压测和监控体系进行公平对比。

### 3.2 UI 应支持哪些实例配置

| 配置类别     | 建议 UI 可配置项                                | 生效方式           |
| -------- | ----------------------------------------- | -------------- |
| Java 运行时 | JDK 8、JDK 21，以及已构建并验证的镜像版本                | 通常需要重建或替换容器    |
| JVM 堆    | `-Xms`、`-Xmx`                             | 重启 JVM 生效      |
| 垃圾回收     | 已验证支持的 GC，例如 G1、Parallel；JDK 版本兼容时才开放其他选项 | 重启 JVM 生效      |
| GC 诊断    | GC 日志、堆转储、OOM 相关诊断选项                      | 多数启动选项需要重启     |
| 线程与运行时   | 可验证的 JVM 参数、线程池参数、连接池参数                   | 按参数性质动态生效或重启   |
| 缓存配置     | Caffeine L1 开关、最大条目数、过期与刷新策略、Redis L2 TTL | 动态切换或按设计重启     |
| 应用韧性     | 熔断、限流、降级开关                                | 动态生效，需明确实例作用范围 |
| 数据连接     | 读写连接池上限、数据库连接模式、Redis 连接模式                | 按实现支持的方式生效     |

UI 不能允许输入任意 JVM 参数后就宣称实验成功。应由后端做参数白名单、类型校验、JDK 版本兼容检查、内存预算校验，并明确显示配置是“已保存”“待重启”还是“已生效”。

### 3.3 一个重要限制：JVM 参数不能全部热修改

例如，`-Xms`、`-Xmx`、GC 选择和部分 GC 日志选项一般属于 JVM 启动参数。改变它们通常需要重启 Java 进程；不能仅靠一个普通 HTTP 开关让正在运行的 JVM 全面换配置。

因此 UI 提供两个操作阶段：

1. 配置实验：为每个实例选择 JDK 镜像、JVM 参数和应用参数。
2. 应用配置：校验配置后，对目标实例重建或重启，并等待健康检查通过。

另外，切换 JDK 或 JVM 参数时要记录旧配置、目标配置、镜像版本、重启时间和生效结果。否则压测报告无法解释性能变化来自哪次配置。

## 四、必须监控的指标清单

这里建议把指标分成两层：Prometheus 负责统一采集与时间序列，Grafana 负责深入分析，控制台负责实验期间最常用的关键指标和对比结论。 Prometheus + Grafana 不应被替换掉，也不应只放一个外链让用户离开操作台才能看数据。

以下清单结合现有文档已列出的指标、已有仪表盘和 Stage2 需要补齐的观测维度整理。某项指标已经存在，不代表当前 UI 已显示；某项指标缺失，也不能通过绘制一个固定数字来代替真实采集。

### 4.1 Benchmark 与 HTTP 服务指标

| 指标                       | 展示方式          | 用途                |
| ------------------------ | ------------- | ----------------- |
| 请求总量、请求速率 RPS            | 实时曲线、实验汇总     | 观察吞吐能力            |
| HTTP 成功率、失败率             | 百分比、按状态码拆分    | 观察稳定性             |
| 响应时间 P50、P90、P95、P99、最大值 | 时间曲线、run 汇总   | 判断尾延迟与抖动          |
| HTTP 状态码分布               | 2xx、4xx、5xx 等 | 识别限流、业务失败和服务端错误   |
| k6 VU、迭代数、请求数            | 实时曲线          | 确认压测负载是否按计划执行     |
| k6 超时、连接错误、检查失败          | 数量和比例         | 识别服务端及网络问题        |
| 预设阈值与阈值判定                | PASS / FAIL   | 统一 benchmark 通过标准 |

需要注意：你当前文档已记录 WSL2 下 cAdvisor 的部分容器网络序列可能不完整。因此，不能把“有 cAdvisor”直接等同于“所有容器网络指标一定齐全”；验收要基于真实序列。

### 4.9 熔断、限流与降级指标

- 每个 Java 实例的熔断器状态：CLOSED、OPEN、HALF_OPEN（按实际组件支持情况）。
- 熔断调用次数、失败率、慢调用率、状态切换次数。
- 限流请求数、拒绝数、通过数、拒绝比例。
- 降级响应数量、降级原因、恢复情况。
- 每实例的开关配置和实际生效状态。
- 与 DB fallback、连接池压力、HTTP P99 的时间关联。

这些指标不仅要在 Grafana 中可见，也应通过控制台按实例显示。当前文档明确指出部分应用运行时开关被 Nginx 和代理白名单阻挡，所以这项需求包含后端访问链路和 API 白名单改造，而不只是前端页面。

### 4.10 实验结果与业务正确性

每次 benchmark 除性能数据外，还应生成业务判定：

- 配置信息快照 和相关描述
- 压测发起量、成功量、失败量。
- 订单新增量与实际数据库记录数。
- 库存基线、剩余库存、扣减量。
- 幂等键重复情况。
- 异步队列是否完成排空。
- 超卖检测结果。
- k6 阈值结果与业务对账结果分别判定。

当前文档特别指出 `stock_oversold_total` 虽已注册，但实际生产路径并未递增，因此不能只看该指标为 0 就宣称没有超卖。Stage2 应修复该指标，或者使用真实的库存与订单对账来判定；推荐两者都做。

### 5.2 必须区分目标数量和实际数量

UI 中输入的“Redis 目标 10,000 个 key”，不能直接当成 Redis 已经有 10,000 个 key。

应当设计完整流程：

1. 用户设置目标数量、数据类型和 TTL。
2. 后端按数量生成指定前缀的实验数据。
3. 可选执行预热。
4. 查询 Redis 实际业务缓存键数量。
5. 查询每个 Java 实例的 Caffeine 实际条目数。
6. 显示目标数、实际数、差值和数据生成结果。
7. 开始 k6 benchmark，并在报告中记录实验开始时的真实数量。

Caffeine 有最大容量与过期机制，条目可能被淘汰；Redis 也可能因为 TTL 或内存淘汰而减少条目。因此，目标数量代表实验规模，实际数量代表观测结果，两者必须分别展示。

此外，Caffeine 是每个 JVM 实例自己的本地缓存。app-1、app-2、app-3 的 Caffeine 条目数、命中率和驱逐次数必须分开统计，不能简单相加后再称为“单个实例的缓存容量”。

### 5.3 必须支持的缓存对照实验

| 实验组        | Caffeine L1 | Redis L2 | 验证目标                  |
| ---------- | ----------- | -------- | --------------------- |
| A：完整两级缓存   | 开启          | 开启       | 基准性能                  |
| B：仅 Redis  | 关闭          | 开启       | Caffeine 对延迟、吞吐与回源的影响 |
| C：Redis 故障 | 开启          | 不可用      | L1 能否缓冲故障，以及故障时的降级行为  |
| D：两级缓存均不可用 | 关闭          | 不可用      | 系统回源、降级、限流和错误表现       |

A 与 B 是第一优先级，应当在相同数据集、相同请求模型和相同运行时长下进行公平比较。C 与 D 是故障演练，不能和正常的缓存关闭实验混为一谈。

## 六、k6 Benchmark 的完整需求

### 6.1 UI 配置项

每次压测至少应允许配置：

- 测试场景：基础负载、阶梯压力、突发压力、长稳测试、缓存实验、故障切换、JVM 对比。
- VU 数量、预热时间、正式运行时长、阶段负载曲线。
- 请求比例、测试数据规模、热点键比例及业务参数。
- k6 检查项和阈值，例如请求失败率、P95/P99、吞吐量。
- 目标应用实例和实验配置组。
- 是否启用故障剧本，以及故障目标、开始时间、持续时间、恢复方式。
- 压测结束后是否执行业务对账、数据复位和报告归档。

### 6.2 一次实验的执行流程

1. 配置实验：选择应用实例、JVM 参数、缓存策略、数据规模和 k6 场景。
2. 执行预检查：确认容器健康、镜像版本、实例配置、数据源模式、监控序列和资源预算。
3. 准备数据：生成 Redis/Caffeine 实验数据，完成所需预热，并记录真实键数量和初始库存。
4. 启动 k6：由 UI 发起受控的容器化 k6 任务，生成唯一 `run_id`，记录实际开始时间。
5. 执行故障剧本：按时间线注入故障，记录目标节点、注入结果、实际生效时间和恢复结果。
6. 实时观测：展示请求性能、JVM、线程池、缓存、数据库、消息队列、节点状态和故障事件。
7. 结束与对账：停止流量，等待异步队列按实验要求排空，检查库存、订单和幂等结果。
8. 生成报告：保存实验配置、指标结果、故障时间线、阈值判定和业务对账结论。

正式 k6 应通过后端控制器启动固定版本、参数受限的 Runner，而不是允许浏览器任意传递 Docker 命令。控制器应限制镜像、命令、挂载路径、运行时长、并发任务数量，并保留停止任务的能力。

### 6.3 run_id 与指标关联

每次实验都应保存唯一 `run_id`，并关联：

- k6 的请求与阈值结果。
- Java 实例的配置快照与指标时间窗口。
- 缓存模式和键数量。
- 故障事件和恢复事件。
- 业务对账结果。

当前文档确认 k6 侧已有 `run_id` 标签，但 Java 应用侧尚不能完全按同一 `run_id` 精确过滤。第一阶段可以按 run 的开始、结束时间聚合 Java 指标，并在报告中明确这是时间窗口归集。不要为了简单关联而给所有应用指标添加高基数的 `run_id` 标签。

### 6.4 Benchmark 对比报告

至少应支持任意两次实验对比，逐项展示：

| 对比维度  | 结果                          |
| ----- | --------------------------- |
| 实验配置  | JDK、GC、堆大小、缓存模式、键数量、VU、时长   |
| 吞吐量   | RPS、请求总量、成功量、失败量            |
| 延迟    | P50、P95、P99、最大值             |
| JVM   | 峰值线程数、堆内存峰值或窗口统计、GC 暂停      |
| 线程池   | Active、Queue、Rejected、连接池等待 |
| 缓存    | L1/L2 命中率、回源次数、驱逐数量         |
| 数据库   | QPS/TPS、连接池等待、订单和库存变化       |
| 故障    | 错误窗口、恢复时间、恢复后的性能            |
| 业务正确性 | 超卖、重复订单、库存对账、队列排空           |
| 最终判定  | 性能阈值、业务正确性分别 PASS / FAIL    |

性能测试不能只看平均延迟。相同负载下，吞吐量、P95/P99、错误率、GC 和业务正确性必须一起判断。

## 七、故障注入与演练场景

Stage2 应统一现有场景向导、线程实验、缓存实验和 k6 故障脚本，避免不同模块各自使用不同的操作方式。

| 故障类别     | 需要能制造的故障                         | 必须观测的现象                 |
| -------- | -------------------------------- | ----------------------- |
| Java 实例  | 停止、重启、冻结、恢复                      | 上游错误率、实例摘除、恢复时间         |
| 线程与线程池   | CPU 占用、线程阻塞、线程泄漏、线程池耗尽、死锁等已有实验模式 | 活跃线程、队列、拒绝数、P99、线程快照    |
| JVM      | 堆压力、GC 压力、不同堆和 GC 参数             | 堆占用、GC 暂停、请求性能          |
| Caffeine | 开关切换、容量与过期策略调整                   | L1 命中率、驱逐、L2 请求、DB 回源   |
| Redis    | L2 不可用、主从切换、内存压力                 | 错误窗口、缓存命中、降级、恢复时间       |
| MySQL    | 主节点故障、Router 路由变化、数据库延迟          | SQL 成功率、连接池、错误窗口、恢复时间   |
| 网络       | 延迟、超时、带宽限制、代理启停                  | 超时率、延迟分布、错误恢复           |
| 熔断与限流    | 开关切换、达到阈值、故障恢复                   | 熔断状态、拒绝数、降级数            |
| RabbitMQ | 消费积压及依赖故障场景                      | Ready/Unacked、消费速率、排空时间 |

每个故障操作都应显示目标、执行状态、开始时间、剩余 TTL 或手动保持状态，并提供单项撤销与全局停止能力。手动保持模式应明确显示“不会自动恢复”，并要求用户在实验结束时确认故障已清理。

## 八、实例配置的安全边界与实现方式

为支持 UI 调整 JVM 和应用参数，建议增加统一的“实例配置管理”能力，但不要让前端直接编辑 Compose 文件或任意执行容器命令。

建议分为三类配置：

1. 启动配置：JDK 镜像、`JAVA_TOOL_OPTIONS` 或白名单 JVM 参数、容器内存限制。保存后由后端生成受控配置，并重建目标容器。
2. 运行时配置：Caffeine 开关、缓存实验模式、熔断与限流等支持动态更新的参数。通过带认证和审计的应用配置 API 生效。
3. 实验配置：VU、时长、缓存目标数量、故障时间线和阈值。由实验控制器管理，不应混入 JVM 启动参数。

每次变更都必须记录修改前后值、目标实例、操作者、时间、应用结果及失败原因。运行时配置默认按实例生效；如果选择“所有实例”，后端必须显式逐实例下发，并逐个读取生效状态，不能只更新一台就显示全局成功。

另外，当前实验室的 chaos-controller 已拥有 Docker socket 操作能力。Stage2 不应再把一个任意 Docker 命令入口暴露给 UI，而应使用严格的镜像白名单、容器名称白名单、参数校验和操作审计。

## 九、Stage2 的实施优先级

| 阶段               | 主要交付                                       | 验收重点                 |
| ---------------- | ------------------------------------------ | -------------------- |
| P0：观测与实验记录       | 指标目录、核心指标卡、Grafana 集成、实验台账、故障时间线           | 同一 run 能查看配置、指标与事件   |
| P1：缓存实验          | Caffeine 独立开关、Redis/L1 目标规模、预热、实际键数量、L1 指标 | 完成 L1 开启/关闭的公平对照     |
| P2：k6 一体化        | UI 启动/停止、参数配置、阈值、run 对比、历史归档               | 两次 run 可复现并逐项比较      |
| P3：多 JVM / 多实例调优 | 每实例 JDK、JVM 参数、应用配置、重启与健康确认                | 同代码下比较不同运行配置         |
| P4：故障剧本与闭环       | 故障配置、TTL、手动恢复、单项撤销、业务对账                    | 故障注入、恢复、性能与正确性形成完整闭环 |

P0 和 P1 建议优先实施。原因是如果实验期间无法准确看到实例指标和缓存实际状态，即使 UI 已经能启动 k6，也很难对性能差异得出可信结论。

## 十、最终验收标准

Stage2 至少应通过以下验收：

- 从控制台配置并启动一次 k6 测试，无需手动进入终端执行正式压测命令。
- 能在操作台直接查看 Prometheus 关键指标，并进入 Grafana 深入分析。
- 能按实例查看 JVM、线程池、连接池、缓存及业务指标。
- 能为不同 Java 实例配置不同的已验证 JDK 版本、堆参数和应用配置。
- 三个实例业务代码版本一致，实验报告中可确认源码版本和镜像版本。
- 能切换 Caffeine L1，控制 Redis 与 Caffeine 实验数据规模，并显示目标数和实际数。
- 能完成 Caffeine 开启与关闭的同负载对照，并输出指标差值。
- 能手动制造故障、看到影响、执行恢复，并确认恢复成功。
- 能对比任意两次实验，并保存完整配置、指标和故障事件。
- 能根据真实业务数据判断库存、订单、幂等和异步队列的正确性，而不只依赖性能阈值。
- 实验结束后能恢复实例、清理故障状态，并按需复位测试数据。

## 十一、范围确认结论（2026-10-27，用户确认，与本文其余条款冲突时以本节为准）

1. **台账持久化**：复用栈内 MySQL（standalone `jl-mysql`；db-ha 经 Router 6446），不引入独立嵌入式库；复位与账表目标按拓扑解析（与改造方案 B0 复位口径一致）。
2. **控制台信息架构**：一次性重构为侧边导航工作区（按 §2.2 信息架构），现有功能组件逐步挂接迁移，不为换 UI 重写已可用能力。
3. **内置基础商品数据**：数据库内置 10,000 条基础商品由**固定 seed 确定性生成**（库存随 seed 随机、每次重置结果相同）；数量与 seed 外置为配置，默认 10000 与固定种子。是否替换商品 1/20 演示基线、库存具体区间**遗留待确认**。
4. **`stress` / `soak` 的 UI 启动与参数配置首期不开放**，移入 Future 清单；场景本身保留在文档口径中。
5. **bandwidth 带宽压制毒性暂不做**，UI 隐藏，移入 Future 清单。
6. **chaos-proxy 与 ha/db-ha 维持互斥**：缓存对照 C/D 组（Redis 不可用）默认在 dev + chaos-proxy 场执行，用 Toxiproxy 模拟 Redis 故障；Redis/MySQL 的 HA 切换走独立场景，用容器动作，不叠加 Toxiproxy。
7. **JDK 8 外壳纳入每实例配置**，标记为 `LIMITED-OBSERVABILITY`：支持镜像选择、JVM 启动参数配置、重启生效、容器/进程/GC 日志回读，并作为 jdk-matrix 实验必过项；不承诺运行时热配置回读和完整应用内指标，相关状态显式显示 `READBACK_UNAVAILABLE`，指标用 GC 日志/JMX/外部采集兜底并在报告中标注来源（原因见改造方案 §4.5）。
8. **镜像身份只做最小闭环**：启动/重建后执行一次 `docker compose images` 或 `docker inspect --format '{{.Image}}'`，把 imageTag + imageId 写入 run manifest/报告；重建时显式 `--force-recreate`。不做来源校验、不归档构建日志、不锁 base digest——这是「本次运行镜像身份记录」，不是「溯源证据」。
