# 文档断言必须证伪

## 现象

多份交接/设计文档里写过「X 未实现 / 未接线」，几轮之后代码已经做了，文档没跟上：

- `details/01`、`details/09` 写「Toxiproxy / D6 / D10 / D11 未实现」——实际四者都已合并运行；
- 文档写「`mysql-ha-scrape.yml` 是惰性文件、未接线」——实际已改成 `prometheus.yml` 内联 job；
- 文档写「`chaos_actions_total`/`chaos_reverts_total` 未实现」——它们在 Task 21 就已落地；
- `step-33` 曾写「D 系列面板按 `app=~".*"` 过滤」——被审核证伪（D1/D2/D4 实际按 `instance` + `up{job=~"seckill-app.*"}` 过滤）。

更危险的是反向情况：**代理只在报告里声称做了，实际没提交**（曾出现「4 个提交 + 16 个文件」全不存在）。

## 根因

- 文档是某个时间点的快照，代码却在前进；`doc/` 的断言没有自动校验。
- 生成文档/报告的人（包括子代理）可能把「设计里写了」「我以为做了」当成「代码里有」。
- 跨步骤的全局陈述（「未实现」「未接线」）最容易过时，因为没人负责在每次合并时回改。

## 正确做法

1. **写文档前先证伪**：任何「未实现/未接线/不存在」的断言，必须先 `grep`/`git log` 确认，并写上证据（文件路径、提交号）。
2. **文档头部记代码基线**：`代码基线：<commit>`；行号与断言都只对该提交负责，后续变更以符号名重新定位。
3. **审核按「文档断言」逐条打勾**：独立审核要专门检查交接文档里的数字、端点名、面板名、提交号，发现不符就记 Important。
4. **代理回报必须带原样证据**：`git log --oneline`、`git diff --stat`、真实测试计数；主会话按 `git` 侧证抽查，不只看报告。
5. **变更时同步三处**：代码 → `doc/process/Stage1/step-*` → `doc/design/Stage1/details`（含 Mermaid 图）。`details` 的 README 有一致性清单，按图回访代码。

## 验证

抽查任意一条「未实现」断言：

```bash
git log --oneline -S "类名或配置键" -- code/ | head
grep -rn "配置键" code/ | head
```

有提交/有代码 → 断言过时，立即改文档；没有 → 补证据后保留。

## 出处

- 文档被证伪的实例：`details/01`、`details/09`（修正提交 `c183c58`）
- 审核发现：`step-33` 的标签/面板断言（`feab2b6`）
- 虚假回报事件与对策：`feedback-delegate-to-subagents` 记忆与 `step-*` 回报契约
