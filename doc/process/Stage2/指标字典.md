# Stage2 指标字典（B0-01 · 真机接线审计）

> 审计对象：**正在运行的真机栈**（34 个 jl-* 容器，dev+ha+db-ha 同开）。所有结论以 Prometheus HTTP 只读查询为准，不采信文档存在性。
> - 查询入口：`http://127.0.0.1:8080/prom/api/v1/{query,series,label/__name__/values}`（经 jl-nginx `/prom` 前缀）。
> - 探测时刻（UTC）：**2026-10-27T15:40:07Z**；接线判定窗口：`/api/v1/series?match[]={__name__=~"^<name>$"}&start=<ts-24h>&end=<ts>`（24h 窗口）。
> - 词表全表：`/api/v1/label/__name__/values` 共 **2014** 个导出名（同刻抓取）。
> - 抓取 job 清单：`code/lab/docker/prometheus/prometheus.yml`（15 个静态 job + k6 remote-write）。当前 `up` 实测：14/15 目标为 1，唯一 0 是 `seckill-app-jdk8`（dual-jdk profile 未开）。
> - 命名口径：本表按**导出名**记录；Micrometer 剥 `_info` 后缀、Timer 未开直方图只有 `_count/_sum/_max`（`doc/avoid_common_error/02`），代码名放「导出名（代码名）」列。
> - 状态取值：`OK`=24h 窗口有真实序列并取样；`NO_DATA`=窗口无序列；`未接线`=代码/方案有而抓取或路径不通（含采集端不提供）；`部分`=有序列但缺方案要求的标签/维度。
> - **纪律**：无序列一律显示「无数据」，禁止用固定 0 冒充（方案 §6.1）。空数据语义列写明 0 是否可信。

### a) Stage1 缺口清单（`doc/design/Stage1/details/README.md` §3.2，39 条）中「未接线/口径」类在字典中的对应行

### b) 方案 §6.2 列出但真机查无序列的清单（B0 修复或标 Future 的靶子）

字典 220 行中 `未接线` 25 条、`NO_DATA` 3 条、`部分` 23 条。按去向分组：

**B0 必修（与 §10.4 门禁表对应）**
1. `cache_size` / L1 每实例条目数：词表无（B0-03，Caffeine stats 未绑定 Micrometer）。
2. Sentinel / `jl-redis-1/2/3-exporter` 序列：整 job 缺失（B0-07）。
3. `stock_oversold_total`：接线 OK（series=3）但即时值恒 0，真实递增路径无样本证据（B0-02）。
4. JVM 参数/镜像版本进 run manifest：词表无 `jvm_parameters_info`（B0-08，记录走 manifest 非 Prometheus）。
5. `mysql_cluster_probe_up` 无 member/target 标签（探针与杀主目标无法区分，B0-08）。

**标 Future / 降级（采集端不提供或需新管道，本次 B0 不修）**
- k6 阈值 PASS/FAIL 详情（只进 `summary.json`）；`k6_http_req_duration_avg/med`（remote-write 只导 p95/p99/max）。
- Nginx 状态码分布、upstream 响应时间（stub_status 限制）。
- Toxiproxy 延迟/带宽/断网指标（无 exporter，状态走 API）。
- `mysql_global_status_deadlocks`（MySQL 8.4 移除状态变量）；TPS 的 `com_commit/com_rollback` 细分；查询/事务耗时直方图。
- `redis_role`/复制角色、RabbitMQ `rabbitmq_up`（用通用 `up{job}` 替代）。
- `resilience4j_circuitbreaker_state_transitions_total`、`ratelimiter_passed/rejected_calls_total`（Micrometer 绑定不提供，用 `changes(state)` 与 `seckill_attempts_total{result="rate_limited"}` 替代口径）。
- cAdvisor per-container CPU/内存/网络/OOM：WSL2 下只有 root 级（verify 唯一 WARN 即此）；容器重启次数只能由 `container_start_time_seconds` 派生。

**预期内不算缺口**
- `orders_total` 24h 无序列：scrape relabel 已改名 `orders_created_total`（prometheus.yml:25-28），属预期。
- `k6_seckill_expected_409/429_total`：历史词存在、24h 无 run 属 NO_DATA，非未接线。

### c) Sentinel / HA redis exporter 抓取现状（供 B0-07）

- `prometheus.yml`（只读核对）只有 `redis-exporter:9121` 一个 Redis job；**无** sentinel job、**无** `redis-1/2/3-exporter` job。
- `compose.ha.yml:313-337` 定义了 `jl-redis-1/2/3-exporter` 三台（当前栈 34 容器含它们），但 Prometheus 不抓 → 词表全表（2014 名）grep `sentinel` = **0**；`redis_up` 24h 仅 1 条序列（单机，值 1，无 node 标签）。
- `compose.ha.yml:310-312` 注释明确 sentinel-exporter sidecar **有意未加**（证据走 `sentinel-status.sh`）。
- 对照：MySQL 侧 `mysqld-exporter-ha` job 已内联且 3 member `up=1`、序列带 `member` 标签（24h `mysql_up` series=4）——B0-07 可照此 pattern 为 HA Redis 增加单 job 三 target + member 标签。
- 影响：D11 Redis 面板在 HA 演练时无序可查；§10.4「无序列时阻断或降级 HA 验收」当前按**未过**处理。

### d) k6 指标 run_id 标签现状

- 24h 窗口内有序列的 k6 指标 36 个，**全部带 `run_id` 标签**（逐指标 series 标签实测）。
- 窗口内共 15 个 run_id：`k6-20261027-160742-dbfo`、`k6-20261027-161756-dbfo2`、`k6-20261027-164307-cache1`、`tune-20261027-121356-baseline512`、`tune-20261027-121559-xmx256`、`tune-20261027-121341-probe2`、`probe-smoke-1`、`probe-abs` 及 6 个 `k6-202610270*` 背景/tune 短 run（`/api/v1/series` match `^k6_.*$` 汇总）。
- 注意 1：k6 走 remote-write，序列**没有 `job`/`instance` 标签**，面板变量只能按 `run_id` 过滤，不能用 `job="k6"`。
- 注意 2：`k6_http_reqs_total` 24h 有 **3369** 条序列且带 `url`（含查询串前的完整 URL）标签——与方案 §6.1「低基数、禁原始 URL 标签」冲突，B1 前需在 remote-write 侧 relabel 掉 `url` 或改用 `group`/`flow`。
- 注意 3：`run_id` 维度存在但 app 侧序列无对应标签，k6↔app 关联仍靠时间窗 + `flow`/`scenario`（§3.2 口径的延续）。
