# 设计逻辑

## 演示优先

目标始终是“制造缺陷/故障 → 观察症状 → 处理 → 对比效果”。秒杀只是产生指标的道具；不做生产级鉴权、审计、多租户或录屏/旁白/回放。

## 模块边界与可拆分

- `seckill-core`：Java 8、框架中立；领域、端口、用例、事件。JPA/Flyway/Spring/控制器在 JDK21 外壳。
- 每个域保留 `api/app/domain/infra` 边界；跨域只存 ID，无 JPA 关联；表前缀 `catalog_`、`inventory_`、`order_`。
- JDK8 外壳将在 M5 提供自己的持久化适配器；共享层锁定 `--release 8`。

## 数据一致性

- 库存：条件 `UPDATE ... WHERE available >= qty` + DB `CHECK`，不超卖。
- 订单幂等：`uk_order_idempotency` 唯一键是权威；重复键在非事务包装层重试读取胜者；失败预扣随事务回滚。
- 订单的幂等重试与 `GET /api/orders/{id}` 固定写库，避免 M3 Router 只读副本延迟；产品读走只读池。
- 缓存：Redis 故障视为 L2 miss，降级 DB；Actuator `app` 健康组排除 redis，根健康仍诚实。
- 秒杀：Redis 库存是准入闸门（Lua 原子），DB 条件更新 + `uk_order_idempotency` 是最终背板；消费者只调用既有订单服务，不重复扣 Redis 库存。重复投递由 DB 幂等键收敛；消费者失败时尽力恢复 Redis 库存并标记 FAILED。发布失败时恢复库存、删除幂等/请求键并返回 503。

## 路由与配置

- 主 `DataSource` = `LazyConnectionDataSourceProxy(ReadWriteRoutingDataSource)`；`@Transactional(readOnly=true)` → read，否则 write。
- `DB_WRITE_URL` / `DB_READ_URL` 是 M3 Router 6446/6447 的接入点；当前 dev 两池都指向 `mysql`。
- 新规约：所有运行路径、超时、重试、TTL、池大小、端口从 Task 16 起必须外置可配置；评审必查硬编码。
- 秒杀配置全部位于 `app.seckill.*` / `spring.rabbitmq.*`（见下方审计清单），`SeckillProperties` 启动时校验必填项；Redisson 客户端为 `lazy-initialization=true`，Redis 故障不阻塞应用启动（播种失败仅 WARN）。
- 启动播种使用 `JdbcTemplate` 非只读事务（走写池），避免 Spring Data 只读事务提前初始化读池；`SET NX` 保证三实例只有一实例真正写入，其余 `skipped(existing)`。

## 运行时保护与 toggles

- **每实例内存 toggle**：`AtomicBoolean` + 不可变映射，读无锁；`GET/POST /lab/toggles` 只影响当前实例，方便“一个实例降级、其余正常”的对比；全局广播留给 chaos-controller。
- **手动 Resilience4j 注册表**：不开注解，按 toggle 条件执行，关闭即真正绕过；启动解析实例让 Micrometer 序列在首个请求前存在。
- **限流一次**：`SeckillResilienceGuard` 是唯一 `acquirePermission()` 调用点；降级 supplier 直接指向 `createSynchronously`，不回到 `admit`，无递归/重复限流。
- **预期业务异常不算熔断失败（复审修正后）**：售罄/锁超时抛 `BusinessException`（被熔断忽略）；参数错误/429 在进入熔断前抛出；`BizException(50301)` 基础设施包装故障计入失败率，真实故障累计后打开熔断并降级同步 DB。非 Biz 异常或已打开熔断同样降级。补充 `minimum-number-of-calls=5`，否则默认 100 在 10 格窗口内永远到不了，熔断打不开。
- **toggle 语义**：`mq` 是 Task 16 启动开关的运行时继任者（YAML 用 `SECKILL_ASYNC_ENABLED` 播种）；`lock` 关只跳过 Redisson，Lua 仍原子；`idempotency` 关只跳过 Redis claim，DB 唯一键仍是背板；`cache` 关返回 no-op cache，两级都不读写。
- **健康门**：resilience4j 的 circuitbreaker/ratelimiter health indicator 关闭，实验性 OPEN/耗尽不会让 Docker 把实例判定 unhealthy；根健康仍诚实。

## 观测与演示

- JSON 日志带 trace 关联；Tempo 自动链路；Prometheus 5s 抓取、7d 保留；Tempo 72h；Grafana provisioning 的 D1–D4。
- 实验操作台目前只读（容器/日志）；故障注入、向导、暂停/还原、缓存实验室在 M2/M4 落地。
- 指标：`seckill_attempts{result=accepted|replay|sold_out|lock_timeout|invalid|error|rate_limited|degraded}`、`order_accept_seconds`（histogram + SLO）、`order_consumer_processed{result=...}`、`stock_oversold`、`orders_created_total`、`idempotent_reject_total`、`resilience4j_*`、两级缓存与 Hikari。

## 业务指标与 D4

- **`OrderMetrics` 单一所有者**：集中注册 `orders_created_total` 与 `idempotent_reject`，启动即 0 值；无 userId/orderId/requestId 标签。`OrderTransactionService` 顺序重放 afterCommit +1；`OrderApplicationService` 并发同 key 重输家重读胜者后 +1；同一 REPEATABLE READ 快照保证不漏计/双计。
- **秒杀重放仍独立**：`seckill_attempts{result="replay"}` 是准入层（Redis 幂等键）重放；`idempotent_reject` 是持久订单层信号，MQ 重复投递也会记录。D4 两类都展示。
- **直方图用配置打开**：`management.metrics.distribution.percentiles-histogram.order_accept_seconds=true`，SLO 由 `ORDER_ACCEPT_SLO` 外置；不改 Timer 代码。
- **RabbitMQ 队列标签**：默认 `/metrics` 聚合无 queue 标签；新增 `rabbitmq-queue` job 抓 `/metrics/detailed?family=queue_coarse_metrics`，relabel `rabbitmq_detailed_queue_*` → `rabbitmq_queue_*`；原聚合 job 保留 delivered 计数。
- **D4 变量作用域**：`instance` 只过滤应用面板；RabbitMQ 指标无应用实例标签，不引用变量。熔断状态用 `==1` + displayName 映射 state 文本；命中率用 `clamp_min` 防 NaN。
- **smoke 配置与边界**：环境变量 > `.env` > 默认；不 source `.env`；只走 HTTP，不直连 MySQL/Redis/RabbitMQ；断言秒杀 202/ACCEPTED，mq 关闭时明确失败；每次运行消耗 product 1/20 各 1 件。
- **verify 证据**：重放后断言 `idempotent_reject_total > 0`，并断言带 queue 标签的 ready 序列；`METRIC_WAIT_RETRIES`/`METRIC_WAIT_INTERVAL_SECONDS` 外置。

## k6 压测设计（Task 19）

- **配置唯一来源**：场景只编排流程；URL、路径前缀、id、时长、VU、阈值、超时、轮询全部来自 `lib/config.js`，非法值 init 阶段 fail-fast。
- **单 run_id**：`run.sh` 在宿主机生成一个 `RUN_ID` 并显式传入容器；`options.tags` 使 HTTP/自定义指标/checks/VU 全部带同一标签。直接 k6 多 VU 运行时需手工传 `RUN_ID`。
- **业务拒绝与失败分离**：秒杀 `http.expectedStatuses(200,202,409,429)`，409/429 不计 `http_req_failed`/`flow_errors`，用 Counter 报告；5xx/transport 才进 `server_errors`。
- **不耗库存的读流量**：load/stress/soak 只读 product，login 每 VU 只一次；smoke 用 `per-vu-iterations` 一次一单；spike 是唯一允许打空 product 20 的场景。
- **时长派生**：load 由单个 `LOAD_DURATION` 派生 20/20/60 三段，2m override 自动得到 24/24/72s；stress 用 JSON stages，为后续场景 JSON 复用。
- **阈值传播**：k6 1.3 阈值失败即非零（实测 99），`run.sh` 原样退出；负向测试用 `ERROR_RATE=0` 构造恒假的 `rate<0`，不依赖偶发错误。

## 已知 Minor / 限制

- cAdvisor 在 Docker Desktop/WSL2 无 per-container 序列，D3 容器面板无数据（WARN，已接受）。
- Flyway 11.7.2 对 MySQL 8.4.4 报“未测试”警告；迁移实际正常。
- `GlobalExceptionHandler` 的 catch-all 使未知路由返回 500，而非 404；后续可加 `NoResourceFoundException` 映射。
- `orders_created_total` 依赖 Prometheus relabel（Java client 保留 `_created` 后缀）；relabel 作用于 `seckill-app` job。
- 重复键异常也覆盖列超长等完整性错误；后续可在 core 加长度校验或收窄异常。
- L1 多实例不一致窗口最长 60s；`clear()` 只清本地 L1。
- 操作台日志请求无 Abort/序列保护；Docker 日志 15s 超时可能返回部分内容；无字节上限；容器列表 N+1 inspect。
- Nginx 启动依赖 Prometheus healthy；Prometheus 外部 URL 硬编码为 `http://127.0.0.1:8080/prom/`。
- dashboard `package-lock` 指向 npmmirror；换默认 registry 需重新解析。
- `verify.sh` 的 cAdvisor WARN 只区分“空结果”，Prometheus API 错误也会被当 WARN。
- 秒杀发布使用 `RabbitTemplate.convertAndSend`，未启用 publisher confirm/return；当前只能捕获连接/发布异常，交换机存在但路由丢失时无法感知（后续可加 confirms + DLQ）。
- 秒杀消息失败后已完成补偿并 `default-requeue-rejected=false`，没有 DLQ/重试策略；失败消息被丢弃，仅请求状态 FAILED 可查。
- 请求状态是 JSON 覆盖写，不是原子 CAS；并发重复投递的 CREATED/FAILED 状态理论上可相互覆盖（DB 订单幂等仍保证不重复下单）。
- `order_consumer_processed{result=duplicate}` 依赖创建前查询作为提示；极端并发重复投递可能把两次都计为 created，指标非严格精确。
- Redis 库存 `restore` 是 `EXISTS` + `INCRBY` 两步，非严格原子；人工重置 DB 或删除 Redis 键后两边可能漂移，尚无对账任务。
- 应用在保存请求状态后、发布消息前崩溃会留下 ACCEPTED 请求直到 TTL；消息发布成功但消费者永久失败则请求 FAILED，Redis 库存已恢复。
- 同步 toggle 路径不经过 Redis 库存/MQ（设计如此），`seckill_attempts` 只统计 accepted，不计 sold_out。
- 所有 full-context 测试现在都需要 RabbitMQ（共享 `RabbitMqTestContainer`）；集成测试把 consumer delay 设为 0、锁等待设为 2s/5s 以避免抖动。
- 演示数据会累积：product 1 DB 77、product 2 DB/Redis 99、product 20 DB/Redis **0**（Task 19 spike 打空）、订单 124；尚无 reset 脚本。默认 verify/smoke 的 product 20 秒杀段在恢复前会 409。
- Task 19 k6：spike 的 `k6_seckill_expected_409_total` 聚合 sold out + lock timeout（短跑 4,366），应用侧 `seckill_attempts{result}` 才区分；按 `run_id` 的序列基数 spike 约 2,084（`name`/`url`/`status`/`check` 标签）；默认 `k6_vus_max` 等只有 `run_id`、无 scenario 标签。
- Task 19 k6：`lib/config.js` 在未传 `RUN_ID` 时会生成 id，但 k6 init 每 VU 执行一次，多 VU 直跑可能不同；`run.sh` 总是传一个统一 id。默认 stress/soak 长跑未执行，只做了短 profile 验证。
- Task 18 `idempotent_reject` 也统计 MQ 重复投递（共享持久订单层）；秒杀准入重放仍只记 `seckill_attempts{result="replay"}`。若需严格区分来源，后续可加低基数 `source` 标签。
