# 设计逻辑

## 演示优先

目标始终是“制造缺陷/故障 → 观察症状 → 处理 → 对比效果”。秒杀只是产生指标的道具；不做生产级鉴权、审计、多租户或录屏/旁白/回放。

## 模块边界与可拆分

- `seckill-core`：Java 8、框架中立；领域、端口、用例、事件。JPA/Flyway/Spring/控制器在 JDK21 外壳。
- 每个域保留 `api/app/domain/infra` 边界；跨域只存 ID，无 JPA 关联；表前缀 `catalog_`、`inventory_`、`order_`。
- JDK8 外壳将在 M5 提供自己的持久化适配器；共享层锁定 `--release 8`。

## 数据一致性

- 库存：条件 `UPDATE ... WHERE available >= qty` + DB `CHECK`，不超卖。
- 订单幂等：`uk_order_idempotency` 唯一键是权威；重复键在非事务包装层重试读取胜者；失败预扣随事务回滚。
- 订单的幂等重试与 `GET /api/orders/{id}` 固定写库，避免 M3 Router 只读副本延迟；产品读走只读池。
- 缓存：Redis 故障视为 L2 miss，降级 DB；Actuator `app` 健康组排除 redis，根健康仍诚实。

## 路由与配置

- 主 `DataSource` = `LazyConnectionDataSourceProxy(ReadWriteRoutingDataSource)`；`@Transactional(readOnly=true)` → read，否则 write。
- `DB_WRITE_URL` / `DB_READ_URL` 是 M3 Router 6446/6447 的接入点；当前 dev 两池都指向 `mysql`。
- 新规约：所有运行路径、超时、重试、TTL、池大小、端口从 Task 16 起必须外置可配置；评审必查硬编码。

## 观测与演示

- JSON 日志带 trace 关联；Tempo 自动链路；Prometheus 5s 抓取、7d 保留；Tempo 72h；Grafana provisioning 的 D1–D3。
- 实验操作台目前只读（容器/日志）；故障注入、向导、暂停/还原、缓存实验室在 M2/M4 落地。

## 已知 Minor / 限制

- cAdvisor 在 Docker Desktop/WSL2 无 per-container 序列，D3 容器面板无数据（WARN，已接受）。
- Flyway 11.7.2 对 MySQL 8.4.4 报“未测试”警告；迁移实际正常。
- `GlobalExceptionHandler` 的 catch-all 使未知路由返回 500，而非 404；后续可加 `NoResourceFoundException` 映射。
- `orders_created_total` 依赖 Prometheus relabel（Java client 保留 `_created` 后缀）；relabel 作用于 `seckill-app` job。
- 重复键异常也覆盖列超长等完整性错误；后续可在 core 加长度校验或收窄异常。
- L1 多实例不一致窗口最长 60s；`clear()` 只清本地 L1。
- 操作台日志请求无 Abort/序列保护；Docker 日志 15s 超时可能返回部分内容；无字节上限；容器列表 N+1 inspect。
- Nginx 启动依赖 Prometheus healthy；Prometheus 外部 URL 硬编码为 `http://127.0.0.1:8080/prom/`。
- dashboard `package-lock` 指向 npmmirror；换默认 registry 需重新解析。
- `verify.sh` 的 cAdvisor WARN 只区分“空结果”，Prometheus API 错误也会被当 WARN。
- 演示数据会累积：product 1 库存约 94、订单 6；尚无 reset 脚本。
- MySQL Router 环境变量尚未接入 compose；M3 处理。
- RabbitMQ 为单节点；Nginx/Router 也是单点；已在设计中声明为范围外。
- JDK8 外壳尚未实现；需显式 `release 8`，并与 JDK21 做场景对比。
- 未做 k6、D4、缓存实验室、Redis Sentinel、MySQL Cluster、线程实验室、调优台、动画大屏、Mermaid 全量图、readme/避坑。
